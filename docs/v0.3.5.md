> full read of the working tree at `9952cc7`. Tick checkboxes as work lands; set each phase's status
> to `Done (YYYY-MM-DD)` when its acceptance checks pass.
>

## 1. Findings

Everything below was verified against the tree, not inferred. File references are
`path:line` at commit `9952cc7`.

### 1.1 Light mode is structurally broken (one line)

- `apps/web/src/routes/__root.tsx:70` renders `<body className="dark">` — hardcoded, never removed.
- `apps/web/src/routes/__root.tsx:62` and `apps/web/src/features/profiles/settings-page.tsx:78`
  both toggle `.dark` on `document.documentElement`.
- `apps/web/src/styles.css:8` defines `@custom-variant dark (&:is(.dark *))`, and
  `styles.css:155` puts every dark token under `.dark`.

Because `body` permanently carries `.dark`, every element in the tree is a descendant of a `.dark`
element, so both the CSS variables *and* every `dark:` utility resolve dark regardless of the
preference. Choosing "فاتح" in settings persists correctly, flips `html.dark` correctly, and
changes nothing visible. The light palette in `styles.css:61-149` has never actually rendered.

### 1.2 There are two competing focus systems

| System | Where | How it registers |
| --- | --- | --- |
| **Explicit** | `features/platform/components/work-card.tsx:100` via `useSpatialFocusable` | React hook, per component |
| **Automatic** | `features/platform/spatial-navigation.tsx:140-244` (`AutomaticSpatialTargets`) | `MutationObserver` on `document.body` → `querySelectorAll` sweep → `SpatialNavigation.addFocusable` per node |

The automatic scanner runs on **every DOM mutation anywhere in the document**, subtree-wide, plus
an attribute filter on five attributes. On each pass it re-queries six selectors across the whole
document, diffs a `Map<HTMLElement, string>`, and calls `getClientRects()` on every candidate —
that is a forced synchronous layout per candidate, per scan. On a laptop this is invisible. On an
Android TV WebView, a rail that lazily swaps forty poster `<img>` elements will trigger dozens of
full-document scans with a layout flush each.

It is also *disabled on exactly the routes an admin uses* (`spatial-navigation.tsx:181-182` skips
`/admin` and `/player/`), which means admin is already keyboard-only-by-accident rather than by
design — useful, because Display Mode wants admin hidden anyway.

### 1.3 There are four different "this is focused" visual treatments

1. `styles.css:331` — global `outline: 3px solid var(--primary); outline-offset: 4px` for
   `[data-spatial-auto][data-focused]`.
2. `work-card.tsx:160` — `ring-[3px] ring-primary ring-offset-2` plus `scale-[1.04]` and
   `-translate-y-1`.
3. `components/ui/button.tsx:8` — Base UI's `focus-visible:border-ring focus-visible:ring-[3px]
   ring-ring/50`.
4. Ad-hoc `focus-visible:` rules in 20 further files (`player-controls.tsx` has 7,
   `sidebar.tsx` has 5, `studio-lineage-page.tsx` has 3).

None of these is a filled, high-contrast selection the way Steam Big Picture, Netflix, or the
Android TV leanback guidance describe it. All four are *outlines on an unchanged surface*, which
is precisely the treatment that stops reading from three metres away.

### 1.4 The API pages in JavaScript, not SQL

`apps/api/src/repository.ts:477` (`browse`):

- Selects **every** matching title with no SQL `LIMIT`/`OFFSET`.
- Calls `relatedData()` (`repository.ts:57`) — ten more queries — for *all* of them.
- Filters visibility in JS, sorts in JS, then `items.slice(offset, offset + limit)` at the end.

So a request for 24 titles loads the entire catalog and its installments, scores, genres, tones,
tags, countries, planets, aliases, credits, and awards. At 194 titles this is survivable; it is
still ten multi-thousand-row queries per page view, and the poster/banner/logo lookups are three
correlated subqueries per row on top.

`repository.ts:574` (`titleDetail`) then issues **one episode query per installment** inside a
`Promise.all` over `data.installments` — a textbook N+1.

### 1.5 The client re-downloads the whole catalog, repeatedly

`apps/web/src/server/compat.ts:295` (`allTitles`) fetches page 1, reads `total`, then fires
`ceil(total/100) - 1` further requests **in parallel** and concatenates. `getWorks`
(`server/library.functions.ts:45`) is that function, and it is called by:

- `features/awards/awards-page.tsx:18`
- `features/awards/award-detail-page.tsx:16`
- `features/library/compare-page.tsx:63`
- `server/compat.ts:512` (planets)

`features/platform/database-page.tsx:186-210` does the same thing for the browse page via four
separate whole-catalog queries. `browseQuerySchema` (`packages/contracts/src/index.ts:205`) caps
`limit` at 100 — the client simply loops past it.

`server/compat.ts` is 713 lines whose entire job is reshaping v2 API responses back into v1 `Work`
shapes. It is the single largest piece of legacy left in the web app.

### 1.6 Nothing is virtualized, and images are half-lazy

- Zero uses of any virtualization library (`@tanstack/react-virtual` is not a dependency).
- 45 `<img>` tags; only 24 carry `loading`/`decoding` hints.
- The browse page renders every title in one grid.

## Phase B — Two modes: Normal and Display

> **Answer to "can we do that?": yes, and it is the right shape for this app.** The important
> design decision is *what a mode actually is*, because the wrong answer means maintaining two
> apps.

### B1. What a mode is (and is not)

A mode is **not** a second route tree, a second component library, or a fork of the pages. It is:

1. A **layout density and interaction contract** applied at the shell level.
2. A **route visibility filter** (Display Mode hides, never deletes, admin and desk-only surfaces).
3. A **capability flag** that individual components may read to swap a heavy affordance for a
   TV-appropriate one.

Concretely: one `AppModeProvider` near the root, one `data-mode="normal" | "display"` attribute on
`<html>`, and Tailwind variants keyed off it. Pages stay single-source; a rail is the same rail,
it is just bigger, has no hover state, and has a different focus treatment.

```
apps/web/src/lib/app-mode.tsx
  ├─ AppModeProvider           reads preference, writes html[data-mode], exposes context
  ├─ useAppMode()              → { mode, isDisplay, setMode }
  └─ <DisplayOnly> / <NormalOnly>   tiny render guards for the handful of real divergences
```

```css
/* styles.css */
@custom-variant tv (&:is([data-mode="display"] *));
@custom-variant desk (&:is([data-mode="normal"] *));
```

Usage stays declarative and reviewable: `class="text-sm tv:text-lg"`, `class="gap-3 tv:gap-6"`.

### B2. What Display Mode changes

| Area | Normal | Display |
| --- | --- | --- |
| Base type scale | 14–16 px | 18–22 px (`html { font-size }` bump via the `tv` variant) |
| Minimum hit target | 32 px | 56 px |
| Focus treatment | ring on an unchanged surface | **filled selection** — see [Phase C](#phase-c--focus-engine) |
| Hover states | full | **none** — `tv:hover:*` is stripped; hover on TV means nothing and causes flicker |
| Admin routes | visible | **hidden from nav and blocked by `beforeLoad`**, not deleted |
| Global search | inline combobox (`cmdk`) | full-screen overlay with an on-screen keyboard |
| Dialogs / dropdowns | popovers anchored to trigger | full-width bottom sheets or full-screen panels |
| Tables (`work-table.tsx`, admin grids) | rendered | replaced by card rails |
| Charts (recharts) | rendered | **not rendered** — the score radar becomes a static bar list |
| Animations | full | reduced: opacity + transform only, no blur/shadow transitions |
| Backdrop blur | yes | **no** — `backdrop-filter` is the single most expensive thing a TV WebView does |
| Density | up to 8 cards/row | 5–6 cards/row, larger posters |
| Scroll | free | rail-snapped, focus-driven only |

### B3. Which routes exist in Display Mode

| Route | Display Mode |
| --- | --- |
| `/` (home) | ✅ primary surface |
| `/browse` | ✅ redesigned as a rail/grid browser, not a table |
| `/titles/$titleId` | ✅ |
| `/player/$installmentId` | ✅ already D-pad-native |
| `/archive` (My Space) | ✅ |
| `/awards`, `/_entities/*` | ✅ simplified |
| `/profiles`, `/settings` | ✅ simplified — settings is where you leave Display Mode |
| `/compare` | ❌ hidden (desk-only analysis tool) |
| `/admin/*` | ❌ hidden from nav, `beforeLoad` redirects to `/` |
| `/offline` | ✅ |

Hiding is done in two places and both are required: the nav model (so the link is absent) and
`beforeLoad` (so a remembered URL or a deep link cannot land you there).

### B4. Persistence and entry

- [ ] Add `preferences.displayMode: "auto" | "normal" | "display"` to `accountPreferencesSchema`
      in `packages/contracts/src/index.ts`, migrate, and `pnpm client:generate`.
- [ ] **Per-account, server-persisted** — that is the whole point of putting it in settings, and it
      means the TV in the living room and the laptop can hold different postures for the same
      family member only if we also… (see next item).
- [ ] **Per-device override in `localStorage`** (`arcadia:display-mode`), which wins over the
      account preference when set. The TV box sets it once; the laptop never does.
- [ ] `"auto"` resolves to Display when **any** of: `matchMedia("(pointer: coarse)")` **and** a
      viewport ≥ 1280 px wide, Tauri reports an Android target, or the URL carries `?tv=1`.
      Practically: real TVs land in Display; laptops do not.
- [ ] Settings gets an **العرض / وضع التلفاز** section as its own tab, above المظهر.
- [ ] A keyboard/remote shortcut toggles it from anywhere (long-press the menu key, or `Ctrl+Shift+T`
      on desktop) with a confirmation toast, so a family member stuck in the wrong posture can get
      out without navigating a UI built for the other one.

### B5. Should the D-pad be removed from Normal Mode?

**No — but it should stop being a bespoke engine there.** Recommendation:

- In **Normal Mode**, delete `AutomaticSpatialTargets` entirely and rely on the browser's own
  sequential focus (`Tab`) plus roving-tabindex inside rails and grids. That is what shadcn/Base UI
  primitives already implement, it is what screen readers expect, and it removes the
  document-wide MutationObserver from the desk experience completely.
- In **Display Mode**, the focus engine from [Phase C](#phase-c--focus-engine) is the only
  navigation model.

This is the cleanup the user asked about: not "remove D-pad", but "stop running a TV navigation
engine on top of a desktop app". Arrow keys still move within rails and grids in Normal Mode,
because that is standard widget behaviour, not a spatial engine.

## Phase C — The focus engine rebuild

> Target: Steam Big Picture. The specific qualities worth copying are **(a)** the selected item has
> a *filled* surface, not an outline; **(b)** there is exactly one selected thing on screen, always;
> **(c)** the selection moves with a short, consistent, interruptible animation; **(d)** the
> selection is never ambiguous during a transition — it moves, it does not fade out and in
> somewhere else.

### C1. The selection token set

Add to `styles.css`, alongside the existing semantic tokens:

```css
:root {
  --selection-surface: var(--primary);
  --selection-foreground: var(--primary-foreground);
  --selection-ring: oklch(1 0 0 / 0.9);
  --selection-glow: 0 0 0 2px var(--selection-ring), 0 12px 40px -8px var(--primary);
  --selection-scale: 1.06;
  --selection-duration: 180ms;
  --selection-ease: cubic-bezier(0.16, 1, 0.3, 1);
}
```

Two variants, one rule:

- **Chrome selection** (tabs, nav items, buttons, list rows, settings controls): the element's
  background becomes `--selection-surface` and its text `--selection-foreground`. Fully filled.
  This is the "white/primary background" the user described, and it is the one that reads across a
  room.
- **Artwork selection** (poster cards, banner cards): the artwork cannot be tinted, so the card
  gets `--selection-glow` plus `scale(var(--selection-scale))` plus a full-opacity title, while
  every *unselected* sibling in the same rail drops to `opacity: 0.55`. The dimming is what makes
  it unambiguous — Big Picture and the Android TV leanback guidance both do this.

Every focus treatment in the app resolves to one of those two. The four competing treatments in
§1.3 collapse to this pair.

### C2. Replace the DOM scanner with a declarative registry

Delete `AutomaticSpatialTargets` (`spatial-navigation.tsx:140-244`). Replace with:

```
apps/web/src/lib/focus/
  ├─ focus-provider.tsx     one context; owns current focus id + the section graph
  ├─ use-focusable.ts       registers an element; returns { ref, focused, selected }
  ├─ use-focus-section.ts   declares a group (rail / grid / column) + its geometry policy
  ├─ focus-geometry.ts      pure: given a rect, a direction, and candidate rects → next id
  ├─ focus-geometry.test.ts pure unit tests, no DOM
  └─ focusable.tsx          <Focusable> render-prop wrapper for the leaf case
```

Design rules:

1. **Registration is explicit and React-owned.** A component that can be focused says so. No
   `querySelectorAll`, no `MutationObserver`, no attribute sniffing. Registration/unregistration
   happens in `useLayoutEffect`, which is exactly when the component actually exists.
2. **Geometry is cached per section, invalidated on resize and on section content change** — not
   read fresh per keypress. `getClientRects()` never runs inside a keydown handler.
3. **Sections are a graph, not a plane.** A rail declares `onUp`/`onDown` to named sibling
   sections. This is what fixes the `resolveTabPanelEscape` special case
   (`spatial-navigation.tsx:95-112`) — that whole function becomes an ordinary section edge.
4. **Focus memory is per section, per route.** Leaving a rail and returning puts you back on the
   card you left, which is the single biggest "feels native" affordance. The existing
   `rememberedFocusByLocation` map (`spatial-navigation.tsx:22`) has the right idea and the wrong
   granularity — it remembers one thing per URL, keyed on a screen-space centroid.
5. **One selected element, always.** The provider guarantees it. If the currently-focused element
   unmounts, the provider selects the nearest surviving sibling in the same section synchronously,
   not on the next animation frame.
6. **Key handling is one listener on the provider**, not one per element. Arrow, Enter, Escape,
   Back, and the Android TV media keys are translated to intents there.
7. **Scrolling is the section's job.** A rail scrolls itself so the selected card sits at a
   consistent inline offset. `revealSpatialTarget` (`spatial-navigation.tsx:63`) becomes a section
   method with the rail's own geometry, instead of a global function guessing at safe areas from
   `window.innerHeight * 0.18`.

### C3. Whether to keep `@noriginmedia/norigin-spatial-navigation`

**Recommendation: keep the core, drop the React wrapper, own the integration.**

The library's geometry engine is sound and battle-tested; the pain in this codebase comes entirely
from the adapter layer we wrote around it. So: keep
`@noriginmedia/norigin-spatial-navigation-core` as the geometry primitive behind
`focus-geometry.ts`, and drop `@noriginmedia/norigin-spatial-navigation-react` in favour of the
provider above. If `focus-geometry.test.ts` ends up proving the pure implementation is adequate,
dropping the core too becomes a trivial follow-up rather than a rewrite.

Evaluate `@bbc/tv-lrud-spatial` as the alternative during C2 — it is smaller, DOM-attribute-driven,
and used in production on real TV hardware. Decide with a benchmark, not a preference.

### C4. Everything is focusable, and obviously so

The user's "really everything" requirement, enumerated so it can be checked off:

- [ ] Nav items and the profile menu
- [ ] Every card in every rail, and every card in every grid
- [ ] Tabs and tab panels
- [ ] All buttons, including the card hover-tray actions in `work-card-actions.tsx`
- [ ] Selects, switches, checkboxes, sliders (volume, subtitle offset)
- [ ] Text inputs — with an explicit **enter-to-edit / Back-to-exit** model, so arrows do not get
      swallowed by a search box the way `isTextEntryTarget` currently has to work around
      (`spatial-navigation.tsx:47`)
- [ ] Dialog, sheet, drawer, and dropdown contents, with focus trapped inside and Back closing
- [ ] Player controls (already good — `player-controls.tsx` should adopt the shared tokens)
- [ ] Pagination, filter chips, sort controls
- [ ] Empty-state and error-state actions
- [ ] The on-screen keyboard in Display Mode search

### C5. A visible focus contract

Add a dev-only overlay (`?focus-debug=1`) that draws the section graph and the current selection
path. This is how the "geometric jumps still feel imperfect" note carried forward from
`v0.2-roadmap.md` gets closed with evidence instead of impressions.

## Phase D — Performance

> Budget, stated up front, measured on the weakest target: **home route interactive < 2.0 s cold on
> an Android TV box; selection moves within 100 ms of a key press, always; no frame over 32 ms
> while moving through a rail.**

### D1. API — page in SQL

- [ ] **D1a. Push `LIMIT`/`OFFSET` into `browse()`** (`repository.ts:477`). Visibility filtering
      moves into the SQL predicate using the account's policy, so pagination and filtering happen
      in one place. `total` comes from a `count(*) over ()` window, not `items.length`.
- [ ] **D1b. Materialize primary artwork.** The three correlated subqueries per row
      (`repository.ts:492-495`, repeated verbatim in four places) become one
      `title_primary_media` view — or, if `EXPLAIN` justifies it, a small denormalized column
      updated by `purgeUnreferencedMedia`'s existing write path.
- [ ] **D1c. Kill the `titleDetail` N+1** (`repository.ts:574`). One `where installment_id in (...)`
      query, grouped in JS.
- [ ] **D1d. Index audit.** Confirm indexes exist for every hot filter: `titles(sort_title)`,
      `titles(is_private)`, `installments(title_id, position)`, `episodes(installment_id, position)`,
      `media_asset_assignments(title_id, role, is_primary)`, `contributions(title_id)`, and the

### E2. Delete the v1 compatibility layer

`server/compat.ts` (713 lines) plus the `Work`/`WorkStructure` half of
`features/library/model.ts` (666 lines) exist only to translate v2 API shapes back into v1 names.
The v2 contracts are the real types. This is ~1,000 lines of pure translation that can be deleted
by migrating consumers to `@arcadia/contracts` types directly. Do it feature by feature, not in one
commit, and let `pnpm typecheck` be the guide.

### E3. Target structure for `apps/web/src`

```
src/
  app/            router, providers, root shell, mode + theme + focus providers
  components/
    ui/           shadcn primitives (vendored, never hand-edited)
    patterns/     app-level compositions: PageHeader, EmptyState, Rail, StatTile, ...
  features/<name>/
    api.ts        query keys + query/mutation options factories  (one per feature, mandatory)
    model.ts      feature types derived from @arcadia/contracts
    components/   feature-local components
    pages/        route-level components
    <name>.test.ts
  lib/            theme, app-mode, focus/, utils, api client
  routes/         thin file-based route entries: loader + component import only
```

Rules that follow from it:

- A route file does route things: `validateSearch`, `beforeLoad`, `loader`, and a component
  import. No JSX bodies beyond a one-line render.
- `features/*/api.ts` is the only place a query key is written.
- Cross-feature imports go through the feature's public surface, never into
  `features/x/components/y`.
- `server/` disappears; its contents move into the owning feature's `api.ts`. The name has been
  misleading since day one — `CLAUDE.md` already has to explain that they are not server functions.

### E4. Merge the duplicated Archive/Platform components

Collapse the three pairs in §1.10 into `components/patterns/`:
`ContinueWatchingRail`, `UpcomingRail`, `FamilyActivityRail`, each taking a `variant` prop for the
two layouts that genuinely differ. One data hook per concept in `features/archive/api.ts`.

## Phase F — UI/UX unification on shadcn

### F1. A component inventory pass

Before writing anything: list every visual pattern that appears on more than one page (page
header, section header, stat tile, empty state, error state, loading skeleton, classification
badge, score display, person chip, filter chip, action tray, pagination). For each, pick **one**
implementation, put it in `components/patterns/`, and delete the rest. `RailHeader`
(`rail.tsx:81`) and `admin-page-header.tsx` are two solutions to the same problem on opposite
sides of the app.

### F2. Missing shadcn primitives worth adding

Checked against `components/ui/`, these are being hand-rolled today and should be installed via
the `shadcn` skill rather than written:

- `sonner` — there is no toast system at all; mutation feedback is ad-hoc per page.
- `pagination` — the browse page needs it once D2c lands.
- `hover-card` — for person/studio previews currently done with bespoke popovers.
- `scroll-area` — rails hand-roll `scrollbar-none` and mask gradients.
- `resizable` — admin split views.
- `sidebar` is installed but only used in admin; the Display Mode nav may want it.

### F3. Style discipline

- [ ] Eliminate the 92 `!important` overrides. Each one means a component variant is missing —
      add the variant to the primitive instead. `platform-shell.tsx` alone accounts for a large
      share.
- [ ] Reduce the 381 arbitrary bracket values to a documented set of tokens. Sizes like
      `auto-cols-[43%]` (`rail.tsx:114`) are legitimately a design ladder — move them into
      `@theme` as named values (`--rail-col-poster-sm`, etc.) so they are greppable and tunable

- [ ] Zero raw hex; zero non-token `black`/`white` outside the `data-on-artwork` exemption.
- [ ] One motion vocabulary: `--selection-duration`/`--selection-ease` from C1, plus a

### F4. Arabic strings

Move interface vocabulary out of TSX into `@arcadia/i18n`. Do **not** attempt full i18n
infrastructure — the app is Arabic-first by design and adding a second locale is not a v3.2 goal.
The goal is consistency: "مساحتي" should be one constant, not seventeen literals, so a wording
change is one edit. Start with the ~200 strings that appear more than once; leave genuinely
one-off page copy inline.

<a id="phase-g--tanstack"></a>

## Phase G — TanStack modernization

### G1. Loaders everywhere

The single highest-leverage change in this phase. Every route that shows data gets a `loader` that
calls `queryClient.ensureQueryData(...)`:

```ts
// routes/titles.$titleId.tsx
export const Route = createFileRoute("/titles/$titleId")({
  loader: ({ context, params }) =>
    context.queryClient.ensureQueryData(titleQueryOptions(params.titleId)),
  component: WorkDetailRoute,
});
```

This makes `defaultPreload: "intent"` (`router.tsx:19`) real: hovering or D-pad-focusing a card
starts the fetch, so by the time Enter is pressed the detail page has data. On a TV, where the
selection lingers on a card for a second or two before activation, **this alone removes most
perceived latency**. Raise `defaultPreloadStaleTime` from `0` so preloads are not immediately
discarded.

- [ ] Add `queryClient` to the router context (`createTanStackRouter({ context: { queryClient } })`).
- [ ] `pendingComponent` per route, using the shared skeleton patterns from F1.
- [ ] `errorComponent` per route; the root one at `__root.tsx:31` stays as the backstop.
- [ ] Preload on **focus**, not just pointer intent — a `preload` call from the focus provider when
      a card is selected for > 250 ms.

### G2. Query options factories

One `features/<name>/api.ts` per feature, exporting `queryOptions()` objects:

```ts
export const titleKeys = {
  all: ["titles"] as const,
  list: (filters: BrowseFilters) => [...titleKeys.all, "list", filters] as const,
  detail: (id: string) => [...titleKeys.all, "detail", id] as const,
};

export const titleQueryOptions = (id: string) =>
  queryOptions({ queryKey: titleKeys.detail(id), queryFn: () => getTitle(id) });
```

Then delete every inline `queryKey: ["works"]`. Invalidation becomes `titleKeys.all` and is
correct by construction.

### G3. Search params as state

`/browse` currently keeps filters in component state and only `q` in the URL
(`routes/browse.tsx`). Move the full filter set into `validateSearch` with a Zod schema, and read
it in the loader. This gives back/forward, shareable filtered views, and — the reason it matters
for TV — a **restorable position**, which is the "Returning means returning" rule that
`v0.3-roadmap.md` set and never fully delivered.

### G4. Mutations

- [ ] Standardize on `useMutation` with `onSettled` invalidation against the key factories.
- [ ] Optimistic updates for the cheap toggles that must feel instant on a remote: favorite,
      watched, save-offline.
- [ ] One `sonner` toast convention for success and failure; delete the per-page alert blocks.

### G5. Decide the SSR-query question

`setupRouterSsrQueryIntegration` (`router.tsx:23`) is dead weight under `spa` mode. Either remove
it, or — the better option if the web build ever gets its own deployment separate from Tauri —
document precisely when it applies. Do not leave it as unexplained ceremony.

<a id="phase-h--android-tv"></a>

## Phase H — Android TV readiness

> Not shipped in v3.2. The goal for this release is that **nothing in the web app blocks it**, and
> that the Rust boundaries are drawn in the right place.

### H1. What already blocks it

- `src-tauri/src/player/surface.rs` embeds mpv via X11 `XID` (`gdkx11`), `#[cfg(target_os = "linux")]`.
- `src-tauri/src/main.rs:13` forces `GDK_BACKEND=x11` and strips `WAYLAND_DISPLAY`.
- `libmpv2` and `librqbit` are unconditional in `Cargo.toml`.

### H2. Work for this release

- [ ] **H2a. Define a `PlaybackBackend` trait** in `src-tauri/src/player/` with the current mpv/X11
      implementation behind `#[cfg(target_os = "linux")]`, so an Android implementation is an added
      file rather than a refactor. The IPC surface the web app talks to (`player_subscribe`, the
      4 Hz `Channel<PlayerEvent>` tick) stays identical — that contract is already good and should
      not change.
- [ ] **H2b. Move `libmpv2` and `librqbit` under target-specific dependency tables.**
- [ ] **H2c. Add the Android manifest additions** (`LEANBACK_LAUNCHER` intent category,
      `android.hardware.touchscreen` not required, `android.software.leanback` feature, TV banner)
      to `src-tauri/gen/android/` when it is generated, and document them in `README.md`. Without
      `LEANBACK_LAUNCHER` the app does not appear on the Android TV launcher at all.
- [ ] **H2d. Key mapping.** Android TV remotes emit `KEYCODE_DPAD_*` and `KEYCODE_BACK`; the System
      WebView surfaces most as standard `ArrowUp`/`Enter`/etc. key events, but media keys and Back
      need explicit handling. The Phase C provider is the single place that translates them —
      write it with a `KeyMap` indirection from day one rather than hardcoding `event.key`.
- [ ] **H2e. Measure on real hardware once.** Even a cheap Google TV dongle running the SPA build
      in Chrome gives a real number for the Phase D budget. Guessing is how TV apps ship slow.

### H3. Backend candidates for Android playback (research, not commitment)

- **Media3 / ExoPlayer via a Tauri Android plugin** — the platform-native answer, hardware
  decoding, and what every Android TV app uses.
- **libmpv on Android** — keeps one player codebase; buildable but heavy, and the surface
  embedding problem is different rather than solved.
- **`tauri-plugin-videoplayer`** — an existing v2 plugin that launches a native player from the
  webview; worth evaluating before writing one.

The torrent side (`librqbit` + the axum stream server in `torrent/stream_server.rs`) is
architecturally portable — it is a local HTTP server, and Android can run it. That part needs
verification, not redesign.

<a id="sequencing-and-acceptance"></a>

## Sequencing and acceptance

Each phase is a shippable increment. Do not start a later phase before the earlier one's
acceptance passes.

| Order | Phase | Why here |
| --- | --- | --- |
| 1 | **A** — correctness fixes | Tiny, unblocks everything, fixes a visible bug today |
| 2 | **E1/E2** — split the giants, delete `compat.ts` | Every later phase edits these files; splitting after would mean doing the work twice |
| 3 | **G** — loaders + query factories | Changes the data-flow shape that D and B both build on |
| 4 | **D1/D2** — API and client pagination | Removes the whole-catalog patterns before adding a second UI mode over them |
| 5 | **C** — focus engine | The centerpiece; needs G's preload-on-focus and D's fast routes to feel right |
| 6 | **B** — Display Mode | Consumes C's tokens and E3's structure |
| 7 | **F** — UI unification | Best done once both modes exist, so the shared vocabulary is real |
| 8 | **D3/D4** — rendering and bundle | Measure against the finished thing |
| 9 | **H** — Android boundaries | Independent; can run in parallel with 6–8 |

### Global acceptance checks

- [ ] `pnpm check` clean, including the new 500-line rule.
- [ ] `pnpm test` clean; new pure-logic tests for `focus-geometry.ts`, the theme resolver, the mode
      resolver, and the paginated `browse()`.
- [ ] `pnpm build` clean; entry chunk under 300 KB uncompressed; no route chunk over 150 KB.
- [ ] Playwright covers: theme toggle round-trip, mode toggle round-trip, a full D-pad journey
      (home → rail → card → detail → play → back, arrow keys only), and admin being unreachable in
      Display Mode.
- [ ] Manual: the whole app driven with **only** arrow keys, Enter, and Escape, in Display Mode, on
      the real Tauri build, from the couch.
- [ ] Manual: light mode reviewed page by page.
- [ ] Every screen has exactly one visible selection at all times.

<a id="ideas-deferred"></a>

## Ideas considered and deliberately deferred

Recorded so they are not re-litigated mid-release.

**Worth doing later, not now:**

- **View transitions** for card → detail navigation. `startViewTransition` would make the Big
  Picture feel land properly, but it is a Chromium-version gamble on the Android System WebView.
  Revisit after H2e gives a real device to test on.
- **A "now playing" persistent bar** in Display Mode.
- **Voice search** via the Android TV remote's mic.
- **A screensaver / ambient mode** — poster slideshow after N minutes idle. Cheap to build, very
  much the Big Picture feel, but it is polish.
- **Per-profile home layouts** (which rails, in what order).
- **Offline-first with a service worker.** The offline feature today is per-title file transfer;
  a real offline-capable catalog is its own release.

**Rejected:**

- **A separate `apps/tv` package.** Two apps means two of every bug fix. The mode contract in B1
  gets the same result with one codebase.
- **Rewriting the player.** `player-page.tsx` and the Rust side are the best-engineered part of
  this repo — rAF-extrapolated playhead, refs instead of state, throttling in Rust before the IPC
  boundary. Adopt the shared focus tokens and otherwise leave it alone.
- **Replacing Tailwind or shadcn.** The problem is discipline, not the tools.
- **Full i18n.** Arabic-first is a product decision, not an oversight.
- **Server-side rendering the web app.** The Tauri constraint that produced `spa` mode is real and
  documented in `vite.config.ts:53-58`; nothing in v3.2 changes it.
